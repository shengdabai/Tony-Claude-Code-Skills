# 网络 / 配置诊断自检（命中网络·代理·多 profile 工具故障时先 Read）

> 来源教训：`feedback_diagnose-self-dependency-loop.md`（2026-06-23 Clash 住宅 IP 一役）。
> 一个任务被切成十几段的根因不是难，是踩了三类自循环陷阱。诊断前先过这三关。

## 三关自检（动手诊断前逐条问）

### 关 1：自依赖——别用坏链路修坏链路
诊断对象 = 我的诊断工具所依赖的链路吗？
- 修代理/网络时还在用 `curl`/`Bash` 走那条正在坏的链路 → 命令反复卡死/abort，任务被切碎。
- 正确：先让用户切到**稳定节点/直连**，或改用**本地文件证据**（配置文件、日志）诊断，不发依赖坏链路的网络请求。

### 关 2：生效态——「存在」≠「runtime 生效」
多 profile / 多配置工具，先锁定**当前真正激活**的那一个再测。
- 反例：对着废弃的旧配置文件猛测 6 次全超时，判「服务死了」——实际早更新、且测的根本不是激活 profile。
- 正确：先查 `current` 指针 + runtime 实际加载 + 真实出口（如真实出口 IP），确认「我测的就是生效的那条」。

### 关 3：落盘真实性——抖动网络下 harness 回执不可信
网络不稳时 Write/Edit 回「成功」但文件可能没真落地（往返被掐，本地动作未必执行）。
- 关键改动（ledger / memory / 配置）写完**必 grep 磁盘复核**，不信「file updated successfully」回执。
- 配合 Cardinal Rule 7：只认真实 result，绝不脑补成功。

## 一句话
网络/配置类故障，先判「我会不会用坏的修坏的」「我测的是不是生效的那条」「我写的有没有真落地」——这三关比急着试命令更省时间。
